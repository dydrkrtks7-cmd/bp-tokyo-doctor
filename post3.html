검색 급락 뒤 첫 72시간: 복구 약속 대신 원인을 좁히는 순서

트래픽 급락 직후 72시간 동안 섣부른 백링크 거부나 URL 삭제로 사이트를 더 망치는 대신, 배포 이력과 상태코드, 색인 설정, 서치콘솔 분할 데이터를 통해 기술적 결함과 알고리즘 변동을 분리해 진단하는 순서를 정리한다.

트래픽 급락 직후 판을 엎는 자들의 헛발질

트래픽 그래프가 바닥으로 꺾이면 다들 이성을 잃는다. 며칠 전 배포한 자바스크립트 설정이나 서버 에러는 거들떠보지도 않고, 인터넷 구석에서 주워들은 72시간 긴급 회복 프로토콜 같은 허황된 처방을 찾아 헤맨다. 멀쩡한 백링크를 모조리 거부 파일에 털어 넣거나 서치콘솔 삭제 도구로 URL을 날려버리는 식이다. 옆에서 지켜보고 있으면 안타깝지도 않다.

구글은 사이트 순위가 떨어졌다고 72시간 안에 마법처럼 원상 복구해 주는 긴급 복구 버튼을 운영하지 않는다. 72시간이라는 숫자는 구글이 움직이는 시간이 아니라, 운영자가 패닉에 빠져 사이트를 완전히 망가뜨리기 전에 자체 결함을 가려내는 초동 점검 시간일 뿐이다.

초동 24시간: 구글 탓하기 전에 배포 이력부터 대조한다

알고리즘 감점이라고 울부짖는 사고의 상당수는 외부 요인이 아니라 내부 배포 사고에서 출발한다. 검색엔진을 탓하기 전에 코드 변경 기록과 서버 접근 로그를 먼저 열어야 한다.

  • 색인 차단 메타 태그 누출: 스테이징 환경의 noindex 설정이나 robots.txt 차단 구문이 배포 과정에서 그대로 상용 서버에 덮어씌워졌는지 확인한다.
  • HTTP 상태 코드와 서버 지연: 5xx 서버 에러나 게이트웨이 타임아웃이 발생해 크롤러가 문전박대당하지 않았는지 웹서버 에러 로그를 확인한다.
  • 정본 주소 꼬임: 정본(canonical) 태그가 엉뚱한 경로를 가리키거나 무한 리다이렉트 루프를 만들지 않았는지 점검한다. URL 삭제 도구는 정본 교정용 도구가 아니므로 여기에 손대면 상황만 꼬인다.

48시간 지점: 서치콘솔 지표를 쪼개서 본다

사이트 전체가 가라앉았는지, 특정 페이지 묶음만 떨어졌는지 분리해서 봐야 한다. 전체 노출이 줄었다고 사이트 전체에 제재가 떨어진 것은 아니다.

서치콘솔 실적 화면에서 급락이 시작된 시점을 기준으로 데이터를 비교 분석해야 한다. 단순히 고정된 기간을 잡기보다, 실제 트래픽이 꺾인 시점부터 변화가 관측된 시점까지 충분히 넓게 보는 게 핵심이다. 검색어, 페이지, 국가, 기기별로 쪼개어 특정 디렉토리나 몇 개 URL만 하락했다면 해당 페이지의 최근 수정 내역이나 경쟁 문서의 검색 의도 변화를 확인한다. 반면 전 페이지의 노출과 클릭이 고르게 내려앉았다면 서치콘솔의 직접 조치 리포트를 열어 수동 페널티 여부를 즉시 확인해야 한다.

72시간 지점: 수정할 것과 관측할 것의 분리

공식 경고도 없고 명백한 스팸 공격 징후도 없는데 불안하다고 백링크 거부(Disavow) 도구부터 돌리면 사이트를 지탱하던 실질적 링크 신호까지 날아간다. 성급한 수정이 독이 되는 순간과 즉각 개입이 필요한 순간을 구분해 둘 필요가 있다.

기록과 관측이 남는 장사다

코어 업데이트나 품질 평가 변동에 따른 순위 조정은 며칠 만에 끝나지 않는다. 구글의 재평가 주기에는 수 주에서 수개월이 걸린다. 72시간 동안 해야 할 일은 증명되지 않은 마법을 부리는 것이 아니라, 스스로 저지른 기술적 결함을 지우고 변동 전후의 데이터를 격리해 두는 것이다. 원인을 좁혀두지 않으면 몇 달 뒤 순위가 돌아와도 왜 살았는지, 왜 죽었는지 모른 채 남의 말에 휘둘리게 된다. 나는 그저 지켜볼 뿐이지만, 헛발질로 도메인을 날려먹는 건 결국 본인 몫이다.
