코어 업데이트 뒤 순위 하락, 감점부터 단정하지 않는 진단표

구글 코어 업데이트 직후 순위 하락을 수동 조치, 기술적 정본 결함, 검색 의도 재평가로 분리해 서치콘솔 지표별로 대조하는 실전 진단 기준을 정리했다.

업데이트 알림만 뜨면 응급실 찾는 이들에게

구글 공식 계정에 코어 업데이트 소식이 뜨면 검색 커뮤니티부터 난리가 난다. 트래픽 그래프가 조금만 꺾여도 어딘가에서 감점을 먹었다며 멀쩡한 글을 지우거나 백링크 거부 파일부터 올리는 사람들이 태반이다. 예전에 키워드 수천 개 밀어 넣고 도메인 갈아타며 밤샘하던 시절에도 그런 조급증이 판을 엎었다. 나는 강 건너 불구경하듯 차트 보는 입장이지만, 엉뚱한 곳에 메스를 대서 멀쩡한 사이트를 식물인간 만드는 꼴을 보면 헛웃음이 나온다.

단도직입적으로 말해서 순위가 떨어졌다는 사실만으로 구글이 벌점을 줬다고 단정할 수는 없다. 다른 문서가 더 잘 답하게 됐는지, 수요나 검색 화면이 바뀌었는지, 우리 배포에서 문제가 생겼는지를 함께 대조해야 한다. 당장 칼부터 쥐지 말고 진단기부터 물려봐야 한다.

차트 꺾였다고 패널티라 부르지 마라

먼저 서치콘솔의 직접 조치 보고서에서 실제 조치와 사유가 있는지 확인한다. 보안 문제는 별도 보고서로 살펴본다. 직접 조치가 없다면 수동 조치가 확인되지 않았다는 뜻이지, 기술 결함이나 수요 변화, 다른 검색 평가 가능성까지 지워졌다는 뜻은 아니다.

많은 웹마스터가 알고리즘 변동을 감점으로 착각하고 72시간 만에 복구한다는 해열제를 찾아 헤맨다. 하지만 코어 업데이트는 특정 단어 몇 개 고쳤다고 다음 날 원상복구되는 시스템이 아니다. 시스템이 전체 웹 생태계를 다시 훑고 새 기준을 자리 잡게 하는 데는 몇 주, 길게는 다음 업데이트 주기까지 시간이 걸린다. 성급하게 손을 대면 원래 왜 떨어졌는지 원인 추적조차 불가능해진다.

서치콘솔에서 떼어보는 네 가지 환부

진단하려면 비교 기간부터 제대로 잡아라. 코어 업데이트 진행 중인지 완료됐는지 공식 일정을 확인한다. 구글은 완료 후 최소 한 주가 지난 뒤, 그때의 한 주와 업데이트가 시작되기 전 한 주를 비교하도록 권고한다. 곧바로 앞 주만 대조하면 서로 다른 업데이트 단계가 섞일 수 있다. 배포 사고는 이 비교를 기다리지 말고 즉시 별도로 점검한다.

1. 사이트 전체 침하인가, 특정 URL의 국소 하락인가

전체가 함께 내려갔는지, 몇 개 문서만 내려갔는지부터 나눈다. 전자는 서버·배포·색인 허용 같은 공통 요소와 수요·검색 평가 변화를 함께 볼 이유가 된다. 후자는 해당 URL의 정본, 내용 변경, 검색어 구성과 경쟁 문서를 대조할 출발점이다. 범위만 보고 신뢰도 하락이나 경쟁 문서의 승리를 진단서에 확정해 적지는 않는다.

2. 정본(Canonical)과 색인 상태의 결함

알고리즘을 탓하기 전에 기술적 사고부터 확인해야 한다. 서치콘솔의 URL 검사를 열어 구글이 선택한 표준 URL과 사용자가 선언한 표준 URL이 일치하는지 본다. 엉뚱한 파라미터 URL이나 HTTP 버전이 정본으로 잡혀 색인 신호가 분산된 사례가 수두룩하다.

3. 크롤링 및 서버 응답 이상

업데이트 기간에 트래픽이 몰리거나 서버 점검이 겹쳐 5xx 서버 오류나 DNS 조회 실패가 발생하지 않았는지 색인 생성 리포트에서 확인한다. 검색 로봇이 문지방을 넘지 못해 일시적으로 색인에서 밀려난 것을 두고 알고리즘 저격이라 오판하는 경우가 흔하다.

4. 검색어 수요 자체의 증발

단순히 순위가 유지되거나 1~2계단만 밀렸는데 클릭 수가 반토막 났다면, 해당 키워드의 계절적 수요 감소나 검색 결과 상단 기능(스니펫, 지식 패널 등) 배치 변화로 인한 전체 클릭 파이 축소인지 대조해야 한다.

증상별 실전 진단표

복잡하게 머리 굴릴 것 없이 아래 표대로 환부를 대조해 보면 지금 무엇을 건드려야 할지 각이 나온다.

관측한 증상더 확보할 자료자료를 받은 뒤의 판단
직접 조치 내역이 있음실제 사유·대상·보고서 안내지적된 문제와 수정 내용을 대조하고 안내된 재검토 절차를 확인
일부 URL의 노출만 하락같은 검색어의 전후 실적, 현재 URL 검사와 변경 기록정본·접근 결함이 확인되면 수리하고, 답의 부족이 확인되면 해당 내용 보강
여러 문서의 노출이 함께 하락서버·배포·색인 허용, 업데이트 일정, 검색어 수요 변화공통 결함과 검색 평가를 나눠 확인; 링크 거부부터 일괄 실행하지 않음
제외 URL이나 크롤 오류가 증가실제 오류 유형·응답 로그·검사 시점의도한 제외인지 장애인지 분리하고 확인된 장애만 수정
순위 변화보다 클릭 감소가 큼노출·검색어·기기·국가별 변화와 실제 검색 화면수요와 노출·클릭 경로를 구분; 설명문 교체만으로 회복을 보장하지 않음

패닉 바잉보다 위험한 패닉 수술

업데이트 직후 패닉에 빠진 운영자들이 가장 많이 저지르는 세 가지 실수가 있다. 이 짓만 안 해도 절반은 먹고 들어간다.

  • URL 삭제 도구 남발: 서치콘솔의 삭제 도구는 검색 결과에서 일시적으로 6개월간 노출을 가리는 차단 도구일 뿐, 색인을 물리적으로 지우거나 정본 오류를 해결하는 도구가 아니다. 여기에 URL을 밀어 넣으면 회복될 기회마저 날아간다.
  • 무차별 백링크 거부(Disavow): 과거 스팸성 링크가 일부 섞여 있더라도 직접 조치가 없는 상태라면 구글 알고리즘이 알아서 무시하고 있을 확률이 높다. 확실한 인위적 조작 흔적이 아니면 함부로 거부 파일을 올려 유효한 연결 점수까지 깎아 먹지 마라.
  • 단어 몇 개 바꾸고 색인 요청 연타: 구글에 색인 생성 요청 버튼을 스무 번 누른다고 순위가 올라가지 않는다. 본문의 문맥과 사용자에게 주는 실질적인 가치가 바뀌지 않았다면 크롤러가 다시 와도 같은 자리에 둘 뿐이다.

남들이 차트 보고 한숨 쉴 때 차분하게 로그 까보고 정본 꼬인 것부터 푸는 사람이 결국 살아남는다. 내 사이트가 진짜 어디서 걸렸는지 감이 안 오면 진단서 들고 제대로 된 전문가한테 검진을 맡기든가. 선택은 각자 몫이다.

이 문서의 질문

구글 코어 업데이트 직후 순위가 떨어지면 백링크 거부(Disavow)부터 해야 하나요?

직접 조치가 없다는 이유만으로 링크 상태가 모두 정상이라고 확정할 수도, 하락했다는 이유로 전부 거부할 수도 없다. 서치콘솔에서 특정 URL만 빠졌는지, 전체가 내려앉았는지 먼저 봐라. 정본 오류나 크롤링 결함 확인이 우선이다.
